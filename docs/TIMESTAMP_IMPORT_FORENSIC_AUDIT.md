# TIMESTAMP IMPORT FORENSIC AUDIT

Branch: `feature/historical-fidelity-import`
Date of audit: 2026-08-23
Scope: full read of the import implementation as of commit `2dfc5eb` plus live E2E observations (jobs #20–#23).

---

## 0. Executive summary

The audit answers A–M below against actual code **and** an observed real import.
The single most important finding:

> **The import file we send already carries correct historical timestamps
> (`19.08.2026 16:01 - First Dev.: چطوری خوبی؟`). Telegram accepts it, imports it,
> and then assigns every imported message a NEW server-side date equal to the
> moment of `messages.startHistoryImport`. The original date survives ONLY as
> `fwd_from.date` metadata on each message (with `fwd_from.imported = true`).**
>
> Verified against Telegram Desktop source (`history_item_helpers.cpp`,
> `history_view_element.cpp`, `history_view_bottom_info.cpp`) which shows clients
> display the *server* date on the bubble and expose the *original* date only in
> the forwarded-header tooltip / "imported" label.

This is not a formatting bug in our generator (see §A–§M evidence).

## B. What exact timestamp format is generated

`%d.%m.%Y %H:%M` (dot-separated, no seconds), e.g. `19.08.2026 16:01`.
Produced by `_format_ts()` (import_serializer.py:28-42).

## C. What timezone is used

Source archive stores ISO-8601 UTC strings (`2026-08-19T16:01:52+00:00`).
`_format_ts` treats naive datetimes as UTC and prints them unchanged — so the
file contains **UTC wall-clock times**.

## D. Whether timestamps are converted to UTC/local time

No conversion happens anywhere in the pipeline:

- export writes `isoformat(getattr(message, "date"))` — Telethon returns UTC;
- canonical archive copies the string verbatim;
- `_format_ts` reformats without shifting timezone.

So: file times are UTC, unconverted. (Note: this differs from what WhatsApp
exports look like — local time — but is irrelevant to the observed failure; see §M.)

## E. Whether date parsing is locale-dependent

No. Parsing paths are `datetime.fromisoformat` and `strptime("%d/%m/%Y, %H:%M")`.
No locale involvement. Output formatting uses `strftime` — also locale-independent
for these numeric directives.

## F. Whether seconds are preserved

**Not in the import file** — format truncates to minutes. Seconds ARE preserved
in the canonical archive (`messages.ndjson`) and in verification data. After
observed import, target messages carry second precision but at import-time
values, so source seconds cannot be validated end-to-end via the visible timeline.

## G. Whether messages are sorted before writing the import file

Yes, ascending. The serializer reverses newest-first ndjson into oldest-first
(import_serializer.py:84) and appends in that order. Verified in the actual
file above: 16:01 → … → 06:18 reading downward means ascending order was written
top-down? No — inspection shows the file starts at `16:01` and ends at `06:18`,
i.e., **descending within the exported slice**. This ordering quirk exists
because the last-10 slice was taken after reversal; the slice selection
(`messages[:limit]` after full-file reverse) takes the OLDEST 10, then the
writer emits them in list order — which here came out newest-of-slice first.
Finding: ordering of lines within the file is NOT guaranteed ascending and must
be made explicitly sorted (timestamp, then source_message_id). Logged as
defect D-1; does not affect the timestamp-placement conclusion (§M) because
Telegram accepted the file, but it is fixed alongside the regression tests.

## H. Whether media rows alter message order

Media references are emitted as their own line `<attached: filename>` directly
after (or instead of) their owning message's text line, sharing the same
timestamp/sender prefix. They do not reorder messages, but each media row
consumes one line of the 100-line `checkHistoryImport` head budget.

## I. Whether sender names alter import parsing

Sender display names are emitted verbatim (`First Dev.`, `RanginKamoon`).
`checkHistoryImport` returned `{pm: true, group: false, title: 'RanginKamoon'}`
— Telegram parsed the chat title correctly from sender names/structure, so
names did not break parsing. Names containing `- ` or newlines could
theoretically confuse the parser; current code strips newlines (`_escape`)
but does not sanitize leading `- ` sequences. Logged as risk R-1.

## J. Whether the first 100 lines passed to checkHistoryImport match the imported file

Yes. `parse_import_head(file_path, max_lines=100)` reads the same
`import.txt` that later goes to `initHistoryImport`. For jobs #22/#23 the whole
file was 10 lines ≤ 100, so head == entire file (byte-identical prefix).

## K. Exact response of messages.checkHistoryImport

Live capture (worker logs, job #22):

```json
{"pm": true, "group": false, "title": "RanginKamoon"}
```

Constructor: `messages.historyImportParsed#5e0fb7b9 flags:# pm:flags.0?true group:flags.1?true title:flags.2?string`.

## L. Exact response of messages.initHistoryImport

Returns `messages.historyImport#1662af0b id:long`. Live run produced a valid
positive `id` (stored in `import_jobs.import_id`, BIGINT). Media uploads via
`uploadImportedMedia` returned concrete tokens, e.g.:

```
MessageMediaDocument(document=Document(id=5789445872957791837, ...,
mime_type='video/mp4', size=1029540, dc_id=4, ...))
```

## M. Exact behavior observed after messages.startHistoryImport

Observed by re-reading the target peer immediately after the RPC returned `true`:

| field | value |
|---|---|
| source text | `چطوری خوبی؟` (source msg 5669281) |
| source date | `2026-08-19T16:01:52+00:00` |
| import file line | `19.08.2026 16:01 - First Dev.: چطوری خوبی؟` |
| **target visible date** | **`2026-08-23T09:35:40+00:00` (= startHistoryImport moment)** |
| target fwd_from | present, `imported: true`, `from_name: 'First Dev.'` |
| target fwd_from.date | equals the historical source timestamp |

All 10 imported messages across jobs #22/#23 show identical behavior:
visible/server `date` == import moment; historical date preserved exclusively
inside `fwd_from.date` metadata. Message ORDER matches the file order.
